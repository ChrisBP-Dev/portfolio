## Desafíos

### 1. `$effect` Gotchas en Svelte 5

**Severidad: MEDIA** — Apareció en 2 de 5 stories (4-1 y 4-3).

- **Story 4-1:** `$effect` trackeaba `content` prop reactivamente → editor destroy/recreate en cada keystroke. Fix: `untrack()`.
- **Story 4-3:** Edit mode mostraba TipTap vacío porque `$effect` de hijos corre antes que del padre en Svelte 5. Fix: `$effect.pre`.

**Root cause:** Svelte 5 runes son poderosas pero tienen edge cases sutiles que solo se manifiestan en runtime, no en unit tests. Falta documentación de anti-patterns específicos del proyecto.

### 2. Discrepancia Spec vs Realidad del Código

**Severidad: MEDIA** — Detectada en Story 4-1.

El epic spec decía "slug auto-generated from ES title" pero `defaultLocale = 'en'` y URLs inglesas no llevan prefijo. El dev descubrió la discrepancia durante implementación y corrigió tanto el blog como un bug pre-existente en ProjectForm.

**Root cause:** El SM creó el spec basándose en el PRD sin verificar cómo funciona el slug system en el código real. La regla `slug-from-EN` se documentó en project-context después del fix.

### 3. Tests Tautológicos

**Severidad: MEDIA** — Apareció en 2 de 5 stories (4-2 y 4-3).

Code review encontró tests que llamaban mocks manualmente y luego verificaban que se llamaron — sin verificar comportamiento real. Reescritos con decision tables y funciones reales.

**Root cause:** El dev siguió patrones de tests existentes que eran superficiales. El code review fue la única barrera que los atrapó.

### 4. Confianza en Verificación

Christopher expresó: "parecen correctos, o eso espero" — indicando que no hay 100% de certeza sobre la correctitud del sistema más allá de lo que los tests cubren. Como usuario intermedio en tecnologías web, confía en el equipo pero no puede verificar independientemente.

**Implicación:** La calidad de los tests y del code review son la principal garantía de correctitud. Los tests deben ser sustantivos, no cosméticos.

## Prompt para Quick-Dev: Orphan Image Cleanup

```
Resolver el defer de "orphaned images on form abandonment" en los 3 forms admin que suben imágenes.

**Problema:** Cuando el usuario abre un form de create, sube imágenes (cover o inline), y luego navega sin guardar, las imágenes quedan en Firebase Storage como orphans sin referencia en Firestore.

**Forms afectados:**
1. `src/components/admin/BlogForm.svelte` — cover image + inline images (uploadedImages array + preGeneratedDocRef)
2. `src/components/admin/ProjectForm.svelte` — main image + screenshots (activeUploads + ImageSlots)
3. `src/components/admin/TechnologyForm.svelte` — logo image (activeUploads + ImageSlot)

**Enfoque:** Cleanup on unmount. En el `$effect` cleanup de cada form, si el form se desmonta sin haber guardado exitosamente, eliminar las imágenes que se subieron durante esa sesión.

**Patrón para BlogForm (más complejo — tiene inline images):**
- Trackear `savedSuccessfully` flag (set true en handleSubmit después del save exitoso)
- En $effect cleanup: si !savedSuccessfully, iterar uploadedImages y llamar imageService.delete() para cada una (non-blocking, try-catch con console.warn)
- También limpiar cover image si coverImageSlot.type === 'new' y no se guardó

**Patrón para ProjectForm y TechnologyForm:**
- Mismo patrón: savedSuccessfully flag + cleanup condicional de imágenes subidas pero no guardadas en $effect return

**Reglas:**
- Non-blocking cleanup — el usuario no debe esperar
- try-catch con console.warn — si falla, orphans quedan (mejor que crashear)
- Solo en create mode o cuando se subieron imágenes nuevas en edit mode que no se guardaron
- No afectar el flujo de guardado exitoso — el flag se pone DESPUÉS del save
- Incluir unit tests para el cleanup behavior
- Incluir E2E test que verifica que el cleanup no interfiere con el happy path
```
