## Éxitos

1. **Admin panel funcionalmente completo** — Auth, dashboard con contadores reales de Firestore, sidebar responsive (desktop/tablet/mobile), CRUD de Projects/Technologies/Experiences con formularios bilingües, gestión de imágenes con zero orphans.
2. **`client:only="svelte"` descubierto temprano (Story 3.1)** — Firebase Auth requiere `window`. Si se hubiera descubierto en la 3.4, habría reescritura de 3 stories. Documentado como regla inmediatamente.
3. **ImageSlot discriminated union (Story 3.3)** — 5 estados (empty/existing/new/replaced/removed) resueltos de forma type-safe. `processImageSlot()` encapsula toda la lógica de imagen.
4. **Safe-first replace pattern** — Upload nuevo → update Firestore → delete viejo. Zero pérdida de datos posible.
5. **Billing spike detectado y resuelto (Story 3.4)** — 12.87GB bandwidth en 5 días por Lighthouse CI descargando imágenes. Fix: skip CI para docs-only commits.
6. **`projectFirestoreSchema` con `safeParse` por documento (Story 3.4)** — Patrón resiliente: documento con datos inválidos se skipea sin crashear la lista. Replicado en Technologies y Experiences.
7. **Centralización de error messages (Story 3.8)** — 6 copias de `getFirestoreErrorMessage()` → 1 utilidad. Primer DRY real en admin.
8. **Svelte 5 runes maduros** — De AuthGuard (3.1) a ExperienceForm (3.7), patrón `$state/$derived/$effect/$props` dominado.
9. **Code review de 3 capas adversariales** — ~38 patches atrapados antes de producción. Schema parsing critical (3.4 P-1) atrapado antes de deploy.

## Problemas Críticos Identificados

### 1. Deferred Items Sin Plan — Replicación de Defectos como Patrón

**Severidad: CRÍTICA**

10 deferred items acumulados durante el epic. De esos, la mayoría fueron justificados como "pre-existente" o "out of scope" **sin plan concreto de resolución**. Resultado: un defecto detectado en Story 3.4 (delete no-atómico) se replicó como "patrón" a 3.5, 3.6, y 3.7. El double-submit se replicó a 3 forms antes de resolverse en 3.8.

**Root cause:** El code review detecta defectos pero el criterio de defer permite justificaciones vagas. "Pre-existente" se usó como excusa para no resolver un defecto conocido, y las stories subsiguientes instruyeron "seguir el patrón existente" — propagando el defecto.

**Impacto:** Deuda técnica exponencial. 1 defecto → 4 archivos afectados. Todos en producción.

### 2. E2E Tests del Admin — Planificados, Diseñados, Nunca Implementados

**Severidad: CRÍTICA**

La arquitectura dice explícitamente: *"E2E de happy paths CRUD"*. El epic spec dice: *"E2E del journey admin (login → CRUD proyecto con imágenes → verificar limpieza Storage)"*. El test-design tiene 7 casos específicos (E-004 a E-010, E-017) diseñados con prioridad P0/P1. **Ninguno fue implementado.**

**Root cause:** El SM no tradujo los E2E del test-design en tareas dentro de las stories individuales. Las stories dicen "minimum tests: unit tests" sin mencionar E2E. El Dev ejecutó lo que la story pedía. El code review validó contra la story. Nadie cuestionó la ausencia.

**Cadena de fallo:**
- Arquitectura → ✅ E2E especificado
- Epic spec → ✅ E2E especificado
- Test-design → ✅ E2E diseñado con IDs
- Stories individuales → ❌ E2E no incluido en tareas
- Dev → Implementó lo que la story pedía
- Code review → Validó contra la story
- **Resultado: 879 unit tests, 0 E2E admin**

### 3. Gap de Verificación Runtime

**Severidad: ALTA**

`pnpm build` para el admin solo genera HTML shells vacíos (`client:only="svelte"`). No toca Firebase, no renderiza componentes, no verifica funcionalidad. La verificación manual fue explícitamente marcada como "left unchecked" en Story 3.1 y nunca compensada. Christopher reportó errores visibles al abrir la app que ninguna herramienta automatizada atrapó.

**Código con errores visibles en runtime está en producción.**

## Desafíos Menores

1. **Accesibilidad mejorada pero no resuelta** — Stories incluyeron tareas explícitas de a11y (action item Epic 2). Pero code review siguió encontrando gaps: `aria-hidden` en SVGs (3.2), WAI-ARIA tabs (3.4), `aria-busy` faltante (3.8), error IDs (3.7). Nivel subió vs Epic 2, pero no es completo.
2. **Error handling inconsistente (Stories 3.4-3.7)** — `getFirestoreErrorMessage()` duplicado en 6 archivos, 2 con fallback incorrecto. Resuelto en 3.8 con centralización.
3. **`prefers-reduced-motion` olvidado (Stories 3.4, 3.5)** — Regla establecida en 3.2 pero no seguida consistentemente. `animate-spin` y `animate-pulse` sin `motion-safe:` prefix.
4. **Memory leaks de ObjectURL (Story 3.4)** — `createObjectURL()` sin `revokeObjectURL()` en replace y destroy. Atrapado en code review.
5. **Documentación inline del código no verificada** — Christopher no domina las tecnologías y confía en que el código sea entendible. No se ha verificado si el código tiene comentarios suficientes para ser auto-documentado.

## Deferred Items — Inventario Completo para Resolución

**Criterio acordado:** Todos se resuelven. Sin excepciones. "Pre-existente" no es justificación válida sin plan concreto.

### Item 1: Delete no-atómico — imagen borrada antes del documento
- **Origen:** Story 3.4 (ProjectsCrudPage), replicado en 3.5, 3.6, 3.7
- **Archivos:** `ProjectsCrudPage.svelte`, `TechnologiesCrudPage.svelte`, `ExperiencesCrudPage.svelte`
- **Problema:** `deleteByPrefix()`/`imageService.delete()` se ejecuta ANTES de `deleteDoc()`. Si Firestore falla, imagen eliminada pero documento persiste con referencia rota.
- **Solución:** Invertir orden: `deleteDoc()` primero, luego delete de imágenes. Si falla delete de imágenes, quedan orphans limpiables — mejor que datos inconsistentes.

### Item 2: Botón "volver" no verifica cambios sin guardar
- **Origen:** Story 3.5 (ProjectsCrudPage), replicado en 3.6, 3.7
- **Archivos:** `ProjectsCrudPage.svelte`, `TechnologiesCrudPage.svelte`, `ExperiencesCrudPage.svelte`
- **Problema:** Botón back-to-list cambia `viewMode = 'list'` sin verificar `hasChanges`.
- **Solución:** Función `navigateToList()` que comprueba `hasChanges` y muestra confirm si hay cambios. Usarla en botón back y en cancel.

### Item 3: Upload task no se cancela al desmontar componente
- **Origen:** Story 3.8
- **Archivos:** `image-service.ts`, `ProjectForm.svelte`, `TechnologyForm.svelte`
- **Problema:** `uploadBytesResumable` retorna `UploadTask` que nunca se cancela si usuario navega mid-upload.
- **Solución:** `imageService.upload()` retorna `{ promise, cancel }`. Forms guardan cancel en ref y lo llaman en `$effect` cleanup.

### Item 4: Multi-image upload sin atomicidad
- **Origen:** Story 3.4, replicado en 3.5
- **Archivos:** `ProjectForm.svelte` (create y edit submit handlers)
- **Problema:** `Promise.all` para screenshots — si falla un upload, los demás ya se subieron sin rollback.
- **Solución:** Cambiar a `Promise.allSettled`. Recopilar exitosos, informar fallidos via toast warning. Actualizar Firestore solo con exitosos.

### Item 5: Document-first create deja orphan si falla imagen
- **Origen:** Story 3.4 (ProjectForm), replicado en 3.6 (TechnologyForm)
- **Archivos:** `ProjectForm.svelte`, `TechnologyForm.svelte`
- **Problema:** `addDoc()` crea documento, si `imageService.upload()` falla, documento queda sin imagen.
- **Solución:** En catch, intentar `deleteDoc()` del documento recién creado (rollback best-effort).

### Item 6: Tests usan patrones imperativos en vez de component rendering
- **Origen:** Story 3.5, replicado en 3.6, 3.7
- **Archivos:** `confirm-dialog.test.ts`, `delete-flow.test.ts`, `edit-form.test.ts`, `technology-*.test.ts`, `experience-*.test.ts`
- **Problema:** Tests validan lógica pura con mocks pero no renderizan componentes Svelte — no verifican interacciones reales.
- **Solución:** Evaluar adopción de `@testing-library/svelte` para component tests. Donde sea viable, agregar tests de rendering para componentes críticos.

### Item 7: Breadcrumb no soporta sub-paths profundos
- **Origen:** Story 3.2
- **Archivo:** `breadcrumb-utils.ts`
- **Solución:** Agregar soporte para paths como `/admin/projects/edit` → "Admin > Projects > Edit".

### Item 8: Sin límite máximo de screenshots
- **Origen:** Story 3.4
- **Archivo:** `ScreenshotManager.svelte`
- **Solución:** Agregar `MAX_SCREENSHOTS = 10` con validación y mensaje de error.

### Item 9: Date timezone offset en inputs de fecha
- **Origen:** Story 3.7
- **Archivo:** `ExperienceForm.svelte`
- **Solución:** Usar `new Date(value + 'T00:00:00')` para forzar interpretación local en lugar de UTC.

### Item 10: BilingualField IDs no siguen convención consistente
- **Origen:** Story 3.7
- **Archivo:** `BilingualField.svelte`
- **Solución:** Agregar prop opcional `idPrefix` para que cada consumidor pase su prefijo.

## Acuerdos del Equipo

1. **Defer solo con plan concreto** — Si el code review encuentra un defecto y no tiene story futura que lo resuelva, se corrige en la story actual. "Pre-existente" sin plan = se resuelve ahora.
2. **E2E obligatorio para flujos de usuario** — El SM verifica contra test-design al crear stories. El Dev no marca 'done' sin E2E de los ACs. Toda story con UI incluye tareas E2E.
3. **Verificación en browser es Definition of Done** — Admin: E2E con Playwright. Público: E2E + Lighthouse CI.
4. **Código auto-documentado** — Entendible sin leer documentos externos. Funciones complejas, decisiones no obvias y patrones del proyecto tienen comentarios inline.
5. **Project context actualizado al cerrar cada epic** — Antes de crear stories del siguiente epic.
