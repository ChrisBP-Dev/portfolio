## Desafíos

1. **Accesibilidad omitida en primera implementación (5/8 stories)** — aria-labels, focus restoration, touch targets, label semántics, Lighthouse CI fallos. Code review lo atrapó consistentemente, pero debería ser parte del desarrollo, no del review.
2. **Suposiciones de datos/schema incorrectas (3/8 stories)** — Story 2.1: colecciones lowercase vs PascalCase, docs obsoletos, colección `projectss` con typo. Story 2.3: ExperienceSection vacía. Story 2.4: Experiences hardcodeadas en Flutter nunca persistidas.
3. **Locale default flip mid-epic (Story 2.7)** — Decisión correcta pero tardía. 14 archivos tocados, todos los tests actualizados. Debió decidirse antes del epic.
4. **Contenido hardcodeado sin plan formal** — Hero (translations.ts), avatar (assets/), resume.pdf, social links (Footer.astro), contact info (.env) — no editables sin deploy, sin story asignada.
5. **Tooling parcialmente resuelto al inicio** — Action item de Epic 1 cumplido parcialmente. Ajustes menores: `tsx` en 2.1, ESLint globals para Svelte en 2.6.
6. **View Transitions + estado de componentes (Story 2.8)** — FOUC, ThemeToggle stale locale con `transition:persist`, MobileMenu portal/scroll leaks. Requirió múltiples patches en code review.

---

## Insights Clave

1. **La calidad profesional empieza en la implementación, no en el review.** Accesibilidad en 5/8 stories fue atrapada en code review. El objetivo es que el code review encuentre issues de arquitectura, no aria-labels faltantes.
2. **Verificar datos reales antes de escribir stories, no asumir desde documentación.** El architecture doc es un plan, no la realidad. 3/8 stories tuvieron datos que no coincidían con suposiciones.
3. **Project context debe actualizarse por epic.** `project-context.md` describe Flutter/Dart (stack anterior). Los agentes recibieron instrucciones de ignorarlo durante todo el Epic 2. Patrón nuevo: epic terminado → project context regenerado.
4. **Decisiones estratégicas antes del epic, no durante.** El locale flip (ES→EN) fue correcto pero tocó 14 archivos mid-sprint. En planificación se habría evitado el retrabajo.
5. **La arquitectura correcta es la pragmática.** JAMstack + Islands es la elección profesional para un portfolio. Clean Architecture / DDD serían over-engineering. Senior engineers eligen la complejidad mínima necesaria.

## Discusión de Arquitectura

Durante la retrospectiva, Christopher preguntó sobre la arquitectura elegida y si demuestra profesionalidad.

**Respuesta del equipo:**

- **Arquitectura actual:** Astro Islands Architecture + SSG + Firebase BaaS (JAMstack moderno)
- **Separación de responsabilidades:** Schemas (Zod) → Data access (collections.ts) → Componentes (domain-organized) → Pages (routing)
- **SOLID aplicado pragmáticamente:** ~89% compliance — Single Responsibility, Interface Segregation, y Dependency Injection bien aplicados
- **Clean Architecture clásica sería over-engineering** para un portfolio con CRUD simple y 4 entidades
- **La elección demuestra madurez técnica:** Senior engineers eligen complejidad mínima necesaria
- **Mejora para Epic 3:** Extraer capa de services (`lib/services/`) para encapsular CRUD admin — sweet spot entre pragmatismo y estructura
